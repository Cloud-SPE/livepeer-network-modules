# v2.0.0 image release

Built from `tasks/lpm-v2` at commit `e9445e8e277c` and published
2026-08-24; every binary is stamped `version=v2.0.0-e9445e8e277c`,
confirmed by pulling the published orch-coordinator and asking it.

Two earlier sets are superseded — `2666f19` and `e92ce32`, both from
2026-08-22. The tag has now moved three times, which is the cost of a
constant tag and the reason to pin digests rather than `v2.0.0`.

This set is the first that carries the fixes the downstream teams are
testing against: the dev keystore signing for real (without it a
chain-free sender and receiver cannot exchange any payment), the
ceiling-division face-value minimum, the job replay returning its
recorded settlement, and the two paid-session wire shapes — `grants`
never null, and a settlement state drawn from the proto's
open/winding_down/closed rather than this broker's internal vocabulary.

## Three tags were moved, not created

`payment-daemon`, `protocol-daemon` and `service-registry-daemon` already
had a `v2.0.0` from 2026-04-28, published under an older numbering scheme
that ran v1 through v4. Those images still exist; they are simply no
longer reachable by tag. Their digests are in
`v2.0.0-preexisting-digests.txt`, which is what makes this reversible.

Worth knowing when reading the registry: the `1.4.x` line is **newer** in
wall-clock time than the old `v2.x`–`v4.x` tags. Sorting the tag list by
version number reads the history backwards.

## Pinning by digest

Compose renders `${REGISTRY}/livepeer-<name>:${TAG}`, and a digest cannot
be substituted through `TAG` — `repo:@sha256:...` is not a valid
reference. Pinning therefore means editing the `image:` lines to
`repo@sha256:...` rather than setting a variable. The digests above are
the values to use.

Left as-is rather than reworked, because changing every stack's `image:`
line to a digest-shaped variable is a deployment-ergonomics decision, not
a build one.
